  • 🚨
    Hora extra exige aprovação prévia — nunca posterior. Comunique ao gestor antes de estender o horário.
  • ⚖️
    Interjornada mínima de 11h — CLT, Art. 66. Saiu às 22h? Não pode ser acionado antes das 9h do dia seguinte.
  • 🚀
    Deploy não justifica entrar cedo — deploy às 7h = hora extra ou reorganização de jornada. Não é "favor ao time".
  • 📝
    Acionamento fora do horário gera compensação — documente e comunique. Se não está registrado, não existe.

    Gestão de Horas
    O que fazer — e o que não fazer
    Deixa claro para todo mundo
    ❌ Não fazer
    ●Trabalhar além do horário sem comunicar ao gestor
    ●Entrar cedo "pra ajudar no deploy" sem registro
    ●Responder chamado às 23h sem anotar o acionamento
    ●Assumir que o gestor "já sabe" que você trabalhou extra
    ●Absorver sobrecarga em silêncio por "sentido de equipe"
    ✅ Sempre fazer
    ●Comunicar ao gestor antes de qualquer extensão de jornada
    ●Registrar todo acionamento fora do horário (hora, motivo, duração)
    ●Planejar deploys críticos dentro do horário comercial
    ●Usar banco de horas quando aplicável e combinado
    ●Se o volume de demanda é insustentável → me falar

    Gestão de Tarefas
    As 5 regras de ouro do board
    Simples e não negociáveis
  • 1
    Mover ao iniciar — assim que você tocou na tarefa, ela vai para In Development. Não "quando terminar o contexto anterior".
  • 2
    Um item por vez — WIP alto é um sintoma de problema, não uma demonstração de esforço. Foco gera velocidade.
  • 3
    PR aberto → Waiting Code Review imediatamente — sem gap entre essas duas coisas.
  • 4
    Flag de impedimento se bloqueado — não avança, mas fica visível. Sem flag = gestor não sabe = não pode agir. Com flag = pode destravar em horas.
  • 5
    Done = em produção — não "o dev terminou". Apenas fechar quando o valor chegou no ambiente final e validado.

    Engenharia de Software
    Princípios que fazem a diferença
    Entregar vs. entregar bem
    🧹
    Clean Code
    Código que você escreve hoje é lido amanhã — talvez por você em 6 meses. Nomes claros, funções coesas. O código deve se auto-documentar.
    🧪
    Testes não são opcionais
    Sem testes, você está empurrando o risco para produção. Se não consegue testar, o design provavelmente está errado.
    📐
    SOLID na prática
    Single Responsibility, Open/Closed, DIP. Esses três sozinhos resolvem 80% dos problemas de arquitetura do dia a dia.
    🔍
    Code Review é trabalho
    PR > 24h sem revisão é problema do time, não do autor. Revisar código é tão importante quanto escrever.
    📊
    Observabilidade
    Toda feature nova: métricas, logs estruturados, traces. Sem observabilidade, incidentes em produção viram caça ao tesouro.
    ⚡
    Débito técnico = dívida com juros
    Todo débito aceito conscientemente precisa de issue no board. Se não está registrado, não existe para o planejamento.

    DoR & DoD
    Os contratos de qualidade do time
    A diferença entre começar certo e terminar de verdade
    📥 DoR — Definition of Ready
    Entra em Dev somente se:
    Objetivo claro — o quê e por quê descritos
    Critérios de aceite — como sabemos que está pronto?
    Estimativa acordada — time entendeu o tamanho
    Dependências mapeadas — sem bloqueio externo
    Acesso e ambiente garantidos
    ✅ DoD — Definition of Done
    Vai para Done somente se:
    Código em produção — no ambiente definido como meta
    Testes escritos e passando
    Code review aprovado — mínimo 1 par
    Critérios de aceite validados
    Observabilidade configurada — logs, métricas, alertas
